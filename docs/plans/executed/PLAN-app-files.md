# Plan: one LexPen.exe and a folder of defaults (the page's code and the .NET files hidden)

Status: executed 2026-10-20 (branch `app-files`); answers of 2026-10-20 worked in (4.1 to 4.3). What was decided
while building, and the start-up measurements: section 5.

## 1. What this is about

`wwwroot` next to `LexPen.exe` mixes two kinds of files. Some are meant to be read, and copied to your own folder
to change: `keys.json`, `settings.json` (the defaults, with a comment per entry), `languages\` and `themes\`. The
rest is the page's code: `index.html`, `app.js` and the other scripts, `app.css`, `settings.html`, and `vendor\`
(CodeMirror, markdown-it, KaTeX, Mermaid). A change to the code breaks LexPen, and nothing in the folder says
which is which. Asked for: the code somewhere nobody changes it by accident, hidden in a .dll if possible, so
the folder keeps only `keys.json`, `settings.json`, `languages\` and `themes\`.

The install folder itself has the same problem: next to `LexPen.exe` are `LexPen.dll`, `LexPen.deps.json`,
`LexPen.runtimeconfig.json`, `Microsoft.Web.WebView2.Core.dll`, `Microsoft.Web.WebView2.WinForms.dll`,
`WebView2Loader.dll` and `YamlDotNet.dll` (the publish folder as it is today). The two json files look like
settings and are not; changing them stops LexPen from starting.

## 2. The solution, in brief

The page's code moves into the project folder `web\` and is built into LexPen as embedded resources; a release
build serves the page from there. The release is published as a single file: `LexPen.exe` holds LexPen.dll, the
two .NET json files, the WebView2 and YAML libraries and the page; only `WebView2Loader.dll` (native) stays next
to it. `wwwroot` is renamed `defaults` and keeps the four things you may read and copy. The install folder then
has `LexPen.exe`, `WebView2Loader.dll` and `defaults\`. A debug build serves the page straight from the project's
`web\` folder, so an edit there applies on a reload, without a build (as the language packs and themes already
do).

## 3. Details

### 3.1 What goes where

| Now | After |
|---|---|
| `wwwroot\index.html`, `*.js`, `app.css`, `settings.html`, `settings.css`, `settings.js` | `web\` in the project; embedded in the exe |
| `wwwroot\vendor\` (generated by `vendor.ps1`) | `web\vendor\`; embedded |
| `wwwroot\keys.json`, `settings.json`, `languages\`, `themes\` | `defaults\` in the project, copied next to the exe as `defaults\` |
| `LexPen.dll`, `LexPen.deps.json`, `LexPen.runtimeconfig.json`, the WebView2 and YAML libraries | Inside `LexPen.exe` (3.3) |
| `WebView2Loader.dll` | Next to the exe, as now |

Nothing of the page reads the four defaults from the page: keys, settings, packs and themes reach it through the
host (`host('keys')`, `host('settings')`, `host('languages')`, `host('look')`). So the page's folder and theirs
can part.

### 3.2 Serving the page from the exe

- `LexPen.csproj`: `web\**` as `EmbeddedResource` with its path as the name (`web/app.js`,
  `web/vendor/katex/fonts/KaTeX_Main-Regular.woff2`), instead of `Content` copied to the output. `defaults\**` as
  `Content`, as `wwwroot\**` is now.
- `MainForm` and `SettingsForm`: instead of `SetVirtualHostNameToFolderMapping`, a `WebResourceRequested` filter
  on `https://lexpen.example/*` answers from the resources, with the content type from the extension (html, js,
  css, json, svg, png, woff2, ttf, ...), 404 for a name that is not there. The address of the page stays the
  same, so the Content Security Policy in `index.html`, the page's own storage (sidebar width, ...) and the tests
  do not change.
- The host's own reads of page files move to the resources too: `app.css` (the theme fallback colours,
  `AppHost`) and `vendor\versions.json` (About).
- Every place that finds the defaults reads `defaults` instead of `wwwroot`: `SettingsFile`, `KeysFile`, the
  language packs and themes (`AppHost.ShippedDir`; a debug build: the project's `defaults\`).
- Size: `vendor\` is the bulk (`du -sh wwwroot/vendor` gave 5.0M today); the exe grows by that, the folder next
  to it shrinks by the same.
- Cost: a resource answer goes through .NET instead of WebView2 reading the file itself; the page loads a
  handful of files at start and Mermaid / KaTeX on first use. Start-up is measured before and after with the
  start-up timing script; the numbers go into section 5 when this is done.

### 3.3 One exe: a single-file publish

- `LexPen.csproj`: `PublishSingleFile` (still framework-dependent: the .NET runtime installed on the PC, as now).
  Native libraries stay out of the bundle (no `IncludeNativeLibrariesForSelfExtract`): `WebView2Loader.dll` is
  next to the exe, so nothing is written to a temp folder. `dotnet publish` then gives `LexPen.exe`,
  `WebView2Loader.dll` and `defaults\`.
- What goes into the exe: `LexPen.dll` (with the page), `LexPen.deps.json`, `LexPen.runtimeconfig.json`,
  `Microsoft.Web.WebView2.Core.dll`, `Microsoft.Web.WebView2.WinForms.dll`, `YamlDotNet.dll`. .NET reads them from
  the exe itself; nothing is unpacked.
- What does not change: `AppContext.BaseDirectory` is still the exe's folder (`defaults\` is found next to it);
  the icon and `tab-colours.json` are resources already. Nothing in LexPen uses `Assembly.Location` (empty in a
  single file; grep of the sources).
- ReadyToRun (on now) works with a single file.
- `register.ps1`, the `.md` association and the published path `C:\Win32App\LexPen\LexPen.exe` stay the same; the
  old files there (`LexPen.dll`, the json files, the libraries, `wwwroot`) have to be deleted once when the new
  version is copied over. The README's publish section says so.

### 3.4 A debug build

Serves `web\` of the project itself (found as the language packs are: up from the exe to `LexPen.csproj`), with
the same folder mapping as now, and reads the project's `defaults\`. An edit to a script applies on F5 in the
page or a new window, without `dotnet build`. The tests keep running the debug build; a separate check runs the
release build once (3.6).

### 3.5 Can it be hidden better than in the exe?

A resource in the exe is not a file anyone edits by accident: changing it means rebuilding. It is not secret: a
.NET resource viewer (ILSpy, dotPeek) shows the scripts, and the page's DevTools would too in a debug build (a
release build has them off already). Hiding the code from a determined reader is not possible for a page that
runs in a browser engine; obfuscating or minifying the scripts is possible but makes errors from the field
unreadable. So: the exe, not more.

### 3.6 Tests

- Unit: every file under `web\` is in the resources, and the name a URL asks for finds it (`app.js`,
  `vendor/katex/katex.min.css`, a font); an unknown name gives none; the content type per extension. The tests
  that read the shipped defaults (keys, settings, packs, themes) read `defaults\`.
- In-app (debug): the full regression set runs as before (the page now comes from the project's `web\`).
- Release build: published to a test folder, started with a test data folder: the page starts, a markdown file

- Start-up: the timing script on the release build, before and after.

### 3.7 Docs

README (Project layout, Build and run, publishing: the three things in the folder, delete the old files once;
every mention of `wwwroot\languages`, `wwwroot\themes`, `wwwroot\keys.json`, `wwwroot\settings.json` becomes

### 5.1 Start-up, before and after

Measured with the release build of each (published to a test folder), a test data folder, a markdown file with a
formula and a Mermaid diagram opened in editor and preview (so the editor, KaTeX and Mermaid all load). Per start
(t57-startup.ps1): **host** = process start to WebView2 navigating to the page; **page** = navigation to the load
event (index.html and its scripts); **ready** = navigation to the last file the page fetched; **total** = host +
ready. One warm-up start first; each start its own process. Medians, in ms (min - max):

| Run | Starts | host | page | ready | total |
|---|---|---|---|---|---|
| Before, alone | 15 | 948 (869 - 2578) | 104 (92 - 126) | 317 (209 - 415) | 1256 (1115 - 2822) |
| After, alone | 15 | 884 (860 - 1043) | 133 (118 - 163) | 400 (365 - 446) | 1286 (1247 - 1489) |
| Before, interleaved | 12 | 900 (848 - 966) | 104 (94 - 121) | 320 (292 - 345) | 1220 (1144 - 1299) |
| After, interleaved | 12 | 888 (844 - 914) | 133 (111 - 362) | 402 (355 - 616) | 1284 (1227 - 1493) |

The interleaved runs (before, after, before, ...) are the fair comparison: total +64 ms on the median. The host
part is the same (the single file costs nothing measurable); the page's files cost more, because each answer goes
through .NET instead of WebView2 reading a file: +29 ms to the load event, +82 ms until the last file (KaTeX and
Mermaid, which load only for a document with math or diagrams).
